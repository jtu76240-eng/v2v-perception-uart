# V2V 사고 정보 전파 시스템의 객체·차선 인식 및 UART 연동

라즈베리파이 5에서 Hailo 기반 객체 인식과 OpenCV 기반 차선 인식을 수행하고, 결과를 중앙 제어용 라즈베리파이에 UART로 전달하는 프로그램입니다.

텔레칩스 차량용 반도체 임베디드 SW 스쿨 3기 1차 프로젝트에서 담당한 인식·통신 부분의 코드입니다. 전체 프로젝트는 5인 팀으로 진행했으며, 이 저장소에는 중앙 제어와 차량 간 무선 통신 코드는 포함하지 않습니다.

## 프로젝트와 담당 범위

- 프로젝트명: 능동형 위기 대응 및 V2V 통신 기반의 사고 정보 전파 시스템
- 기간: 2025.12.10~2026.01.09
- 목표: 전방 장애물 감지와 긴급 제동, 후속 차량으로의 사고 정보 전파
- 팀 성과: 1차 프로젝트 최우수 프로젝트상 수상

이 저장소의 Python 프로그램은 직접 작성한 담당 코드입니다. YOLO 커스텀 학습 및 Hailo용 모델 변환, OpenCV 차선 인식, 멀티스레드 구성과 공유 데이터 동기화, 중앙 제어용 라즈베리파이와의 UART 연동을 수행했습니다. 별도로 하드웨어 부품 선정, 전력 분배망 구성과 차체 3D 설계도 담당했습니다.

## 버전 구분

- 프로젝트 당시 보드에서 실행한 버전: 태그 `project-version` (커밋 `350938a`, 교육기관 제출본)
- 종료 후 변경한 내용: 모델 경로를 스크립트 위치 기준으로 변경, 차선 탐색 시작 창 번호 계산 수정, 주석 정리, README 작성
- 변경 후 보드에서 재확인한 범위: 없음. 차선 탐색 창 수정이 인식 결과에 미치는 영향은 확인하지 않았습니다.

성능 개선 과정의 FPS 수치는 당시 버전에서 확인한 결과입니다.

| 파일 | 역할 |
| --- | --- |
| `ai_final.py` | 카메라 캡처, 객체 인식, 차선 인식, UART 송신을 연동한 통합 프로그램 |

| `lane_tuning.py` | ROI, 원근 변환, 감마 및 차선 탐색 파라미터를 화면에서 조정하는 프로그램 |

교육기관에 제출한 코드를 바탕으로 정리한 저장소입니다. 종료 후 변경 내용은 위 '버전 구분'을 참고합니다.

## 실행 구조

`ai_final.py`는 다음 네 작업을 별도 스레드로 실행합니다.

| 작업 | 처리 내용 |
| --- | --- |
| 카메라 캡처 | Picamera2로 영상을 받아 최신 프레임 공유 |
| 객체 인식 | 최신 프레임을 모델 입력 크기로 변환하고 Hailo 추론 및 결과 처리 |
| 차선 인식 | 1 Hz로 영상 전처리, 색상 마스크, 슬라이딩 윈도우 및 차선 번호 판단 |
| UART 송신 | 객체 결과는 목표 주기 20 Hz, 차선 결과는 1 Hz로 패킷 생성·전송 |

공유 프레임과 인식 결과에는 `threading.Lock`을 적용합니다. 객체 인식과 차선 인식은 각각 최신 프레임을 가져와 처리하며, UART 스레드는 저장된 최신 결과를 읽어 전송합니다.

차선 인식은 노란선·흰선 마스크, 원근 변환, 슬라이딩 윈도우 탐색과 곡선 피팅을 사용합니다. 중앙선·점선·실선의 조합으로 시험 도로의 차선 번호를 판단합니다. 일반 도로 전체를 대상으로 한 범용 차선 인식 모델은 아닙니다.

## 실행 환경과 방법

필요한 장비와 소프트웨어는 다음과 같습니다.

- 라즈베리파이 5와 Picamera2에서 사용할 수 있는 카메라
- Hailo 가속기 및 장치와 호환되는 HailoRT Python 환경
- Python 3, OpenCV, NumPy, Picamera2, libcamera, pyserial
- 영상 창과 튜닝 창을 표시할 수 있는 그래픽 환경
- 통합 프로그램의 UART 송신을 확인할 중앙 보드와 연결 환경

패키지 버전과 설치 절차는 사용 중인 라즈베리파이 OS 및 Hailo 환경에 맞춰 확인해야 합니다. 이 저장소에는 고정된 버전 목록이 포함돼 있지 않습니다.

실행 전 `best.hef`를 `ai_final.py`, `hef_only.py`와 같은 폴더에 배치합니다. 두 프로그램은 스크립트가 저장된 폴더를 기준으로 모델 파일을 읽습니다.

UART 장치와 상대 보드의 통신 설정도 확인합니다.

```python
UART_DEVICE = "/dev/ttyAMA0"
UART_BAUD = 9600
```

`ai_final.py`와 `lane_tuning.py`는 카메라 해상도를 832×832로 설정하고, 장착 방향에 맞춰 180도 회전을 적용합니다. `hef_only.py`는 모델 입력 크기에 맞춰 카메라 해상도를 설정하며, 회전 설정은 적용하지 않습니다. 사용 환경에 맞춰 각 프로그램의 카메라 설정을 확인해야 합니다.

```bash
# 객체 인식 단독 실행
python3 hef_only.py

# 차선 인식 및 파라미터 조정
python3 lane_tuning.py

# 객체·차선 인식과 UART 통합 실행
python3 ai_final.py
```

각 프로그램은 영상 창에서 `q`를 눌러 종료합니다. 모델 파일 배치와 카메라 설정을 확인하고, 단독 실행 프로그램으로 객체 인식과 차선 파라미터를 점검한 뒤 통합 프로그램을 실행합니다.

## UART 패킷

보레이트는 9600입니다. 중앙 보드가 UART 3개와 CAN 2개를 동시에 받는 구조라 중앙 보드 측 사정으로 UART 보레이트를 통일해야 했고, 인식 보드만 115200으로 올릴 수 없어 9600으로 맞췄습니다. 대신 전송 지연을 줄이기 위해 인식 결과를 문자열이 아닌 1바이트 값으로 보내는 등 패킷을 최소 길이로 정했습니다.

패킷은 `struct.pack`을 이용한 리틀 엔디언 형식입니다.

| 구분 | 구성 | 길이 |
| --- | --- | --- |
| 차선 | `0xA1` 1바이트 + 차선 번호 1바이트 + 송신 시각 4바이트 | 6바이트 |
| 객체 | `0xA2` 1바이트 + 객체 유형 1바이트 + 영상 위치 기반 참고값 1바이트 + 송신 시각 4바이트 | 7바이트 |

- 차선 번호는 1·2·3이며, 미확정은 0으로 전송합니다. 차선 사이 상태는 1·2차선 사이를 1, 2·3차선 사이를 3으로 보냅니다.
- 객체 유형은 라바콘(`rubber_cone`, 클래스 ID 5)을 2, 나머지 6개 클래스(H-beam, coil, pallet, tire, human, deer)를 1로 전송합니다. 라바콘은 트럭 등에서 떨어진 유실물로 가정했고, 충돌해도 차량 손상이 작아 긴급 제동 대상에서 제외했습니다. 7개 클래스는 고속도로 낙하물 조사 자료를 참고해 정했으며, 선정 근거는 [V2X 저장소 README](https://github.com/jtu76240-eng/v2x-perception-can)에 정리했습니다.
- 객체는 한 송신 주기당 최대 3개를 전송합니다.
- 시각은 밀리초 단위 시스템 시각의 하위 32비트입니다.
- 객체 패킷의 `dist_m` 변수는 객체 박스 중심의 영상 내 세로 위치로 계산한 참고값입니다. 보정된 미터 단위 거리 측정값이 아닙니다.

수신 측은 패킷 종류와 길이에 맞춰 해석해야 합니다. 중앙 보드의 수신·제어 코드는 이 저장소에 포함되지 않습니다.

| 시험·문제 | 확인 과정과 결과 |

| 빈 도로의 장애물 오검출 | 차량을 세워 둔 상태에서는 나타나지 않았고, 주행 중에 낮은 신뢰도(약 0.3~0.5)로 장애물이 잠깐 검출되는 경우가 간혹 있었음<br>↳ 2차 프로젝트 모델 재학습 시 빈 도로 영상을 추가 |

| 중앙 보드와 UART 통신 | 처음에는 수신되지 않음<br>↳ 중앙 보드 담당자가 확인한 결과, 중앙 보드가 인식 보드와는 9600, 통신 보드와는 115200으로 서로 다른 보레이트를 쓰고 있었음<br>↳ 두 포트를 9600으로 통일한 뒤 수신 확인 |

## 성능 개선 과정

팀은 TTC 계산과 관련된 처리 지연을 고려해, 중앙 보드의 판단 시간 100 ms 중 인식 보드에 할당한 50 ms를 기준으로 객체 인식 목표를 20 FPS 이상으로 정했습니다.

| 단계 | 수행 내용 | 프로젝트 당시 확인한 처리속도 |
| --- | --- | --- |
| 초기 | 라즈베리파이에서 객체 인식 수행 | 약 2 FPS |
| 1차 개선 | AI 가속기 적용 및 NPU용 모델 양자화 | 약 16 FPS |
| 2차 개선 | 차선 인식 실행 주기를 1 Hz로 조정 | 약 36 FPS |

차선 정보는 사고 발생 차선을 후속 차량에 알리는 용도로 사용했습니다. 시험 차량의 낮은 주행 속도와 영상 변화 정도를 고려해 차선 처리 주기를 조정하고, 객체 인식에 사용할 연산 자원을 늘렸습니다.

측정 조건: 라즈베리파이 5에 Hailo 가속기를 장착한 상태에서 통합 프로그램(`ai_final.py`)으로 카메라 캡처, 객체 인식, 차선 인식(1 Hz), UART 송신을 함께 실행하며 화면의 FPS 표시로 확인했습니다. 수치는 프로젝트 당시 버전(`project-version` 태그)에서 확인한 결과이며, 종료 후 수정본에서는 다시 측정하지 않았습니다.

통합 코드의 FPS 표시는 성공한 추론 횟수를 측정 시작 이후 경과 시간으로 나눈 값입니다. 서로 다른 카메라 프레임만 처리하는지 확인하는 로직은 없으므로, 객체 인식 스레드의 처리속도로 해석합니다. UART 전달 및 중앙 제어까지의 전체 지연시간을 나타내지는 않습니다. 이 저장소에는 측정 로그가 포함돼 있지 않습니다.

## 적용 범위와 개선할 부분

- 차선 정확도는 정량 평가하지 않았으며, 직선 구간에서 동작을 확인했습니다. 곡선 구간의 인식 어려움은 후속 프로젝트에서 카메라 시야를 넓히는 방향으로 대응했습니다.
- 차선 검출에 실패하면 이전 결과를 최대 9회 유지합니다. 1 Hz 처리 설정에서는 약 9초간 과거 차선이 사용될 수 있습니다.
- UART 패킷의 시각은 보내는 시점의 시각이며, 중앙 보드가 오래되거나 중복된 패킷을 걸러내는 용도로 중앙 보드 담당자의 요청에 따라 넣었습니다. 다만 객체·차선 결과를 만든 시각은 담지 않아서, 인식 스레드가 멈춰도 UART 스레드가 마지막 결과를 새 시각과 함께 계속 보내면 중앙 보드는 이를 오래된 결과로 걸러내지 못합니다. 결과를 만든 시각을 함께 보내는 것이 개선 대상이며, 2차 V2X 프로젝트에서 보완했습니다.
- 차선 탐색의 구역 번호→탐색 창 번호 변환은 종료 후 수정한 부분으로('버전 구분' 참고), 기본 설정에서는 3개 구역을 15개 탐색 창에 대응시킵니다. 수정이 인식 결과에 미치는 영향은 확인하지 않았습니다.

이 저장소는 교육 프로젝트에서 구현·제출한 인식 및 통신 코드와 적용 범위를 기록합니다. 실제 차량용 제품 수준의 정확도·고장 대응을 검증한 코드는 아닙니다.
